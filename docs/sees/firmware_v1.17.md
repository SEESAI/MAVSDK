## What and why

SeesInterface2 currently uses this fork's `v1.4.11_dev` branch: upstream v1.4.11 plus 20 Sees commits. Firmware v1.17 stops sending the patched `GPS_INPUT` and sends the new `SEES_GPS_RAW` message instead, defined in the Sees MAVLink dialect in [SEESAI/mavlink](https://github.com/SEESAI/mavlink).

Firmware v1.17 is the reference, so this fork moves to upstream **v3.7.0**, the MAVSDK release PX4 v1.17 itself tests against (`test/mavsdk_tests/MAVSDK_VERSION` in Firmware, used by PX4's SITL integration tests in CI).

- v3.7.0 was released against upstream mavlink `5e3a42b8` (December 2024), which is older than PX4 v1.17's `33af200d`. It builds against PX4 v1.17's mavlink with one small source change (see below).
- The latest release, v4.2.1, was tried first. It was released against much newer mavlink and needed a newer pymavlink generator plus source patches in five plugins to build against PX4 v1.17's mavlink. That combination isn't tested by PX4. The attempt is kept only as a local backup branch, `backup/firmware_v1.17-on-v4.2.1`.

MAVSDK changed its API in v2 and v3, so the Sees commits are re-applied on top of v3.7.0 rather than merged.

The MAVSDK and SeesInterface2 changes are done together, because SeesInterface2 can't build against v3 without its own API migration, and the MAVSDK audit decides which Sees features move into SeesInterface2.

While the work is in progress, SeesInterface2's vcpkg port (`REF` in `BuildTools/vcpkg/ports/mavsdk/portfile.cmake`) points at commits on `vilas/feat/firmware_v1.17`. At release, the feature branch is merged into `v3.7.0_dev`, tagged (e.g. `v3.7.0-sees.1`), and SeesInterface2 re-pins to the tag.

Don't force-push `vilas/feat/firmware_v1.17` once SeesInterface2 pins one of its commits, or fresh clones of SeesInterface2 won't be able to fetch it. (It was force-pushed once, on 2026-11-20, to move it from v4.2.1 to v3.7.0, before anything pinned it.)

## MAVLink: the same mavlink as PX4 v1.17

This fork is built against the mavlink PX4 v1.17 uses, SEESAI/mavlink (upstream `33af200d` + `sees.xml`), with the same `sees` dialect. It therefore has `SEES_GPS_RAW` and every message PX4 v1.17 sends, generated by the same pymavlink (`fcaa2c7d`) from the same definitions as PX4.

| Setting | Upstream v3.7.0 | This fork | File |
|---|---|---|---|
| mavlink repository | `https://github.com/mavlink/mavlink` | `https://github.com/SEESAI/mavlink` (`MAVLINK_GIT_URL`) | `third_party/mavlink/CMakeLists.txt` |
| `MAVLINK_GIT_HASH` | `5e3a42b8` | a commit on `33af200_dev`, the same commit Firmware pins (the hash is only in the file). Currently still the pre-merge commit of SEESAI/mavlink#3, which was squash-merged; re-pin to `33af200_dev` (identical definitions) | `third_party/mavlink/CMakeLists.txt` |
| `MAVLINK_DIALECT` default | `common` | `sees` | `CMakeLists.txt` |

Upstream's `third_party/mavlink/mavlink.patch` applies unchanged: it was written against the same mavlink `CMakeLists.txt` that `33af200d` has.

The mavlink settings only apply to superbuilds (`SUPERBUILD=ON`, the default). With `SUPERBUILD=OFF`, as in SeesInterface2's vcpkg port, MAVSDK uses `find_package(MAVLink)` and `find_package(libevents)`. SeesInterface2 supplies both as vcpkg ports:

- `mavlink-seesai`: `sees.xml` from the same SEESAI/mavlink commit, generated with the `sees` dialect;
- `libevents`: at the commit `third_party/libevents/CMakeLists.txt` pins.

When `sees.xml` changes, update `MAVLINK_GIT_HASH` here and the `mavlink-seesai` port's `REF` to the commit Firmware pins. A mavlink commit that doesn't change `sees.xml`, such as a doc change, needs no re-pin.

### Fixes for non-superbuild installs

SeesInterface2's vcpkg port builds this fork with `SUPERBUILD=OFF`, from a source archive (no `.git`), and links it statically. Upstream v3.7.0 needed three fixes for that (marked `SEES`):

| File | Problem in upstream v3.7.0 | Fix |
|---|---|---|
| `src/MAVSDKConfig.cmake.in` | `find_dependency(LibEvents)`, but libevents installs `libeventsConfig.cmake` and MAVSDK's own build uses `find_package(libevents)`. On case-sensitive file systems, every consumer of a static MAVSDK failed to find it | `find_dependency(libevents)` |
| `third_party/CMakeLists.txt` | Always fetched and built its own libevents, even when one is installed | Build it only if `find_package(libevents)` fails; superbuilds are unchanged |
| `CMakeLists.txt` | Without `.git`, the version fell back to `0.0.0`, which the version regexes don't match, so the package version became `0.0.0.0.0.0.0.0.0` | Fall back to `v3.7.0`; update it when moving the fork |

## `SEES_GPS_RAW`: `Telemetry::GpsInput`

The telemetry plugin decodes `SEES_GPS_RAW` into `Telemetry::GpsInput`, ported from `v1.4.11_dev` (#15, #20), where it decoded the v1.13 patched `GPS_INPUT`. SeesInterface2 uses it unchanged:

```cpp
auto handle = telemetry.subscribe_gps_input([](Telemetry::GpsInput gps) { /* one per GPS instance */ });
telemetry.unsubscribe_gps_input(handle);
Telemetry::GpsInput latest = telemetry.gps_input();
```

- **Same struct, same mapping as v1.4.11.** `SEES_GPS_RAW` has the same field names as the v1.13 `GPS_INPUT`, so `TelemetryImpl::process_sees_gps_raw()` fills `GpsInput` exactly as v1.4.11's `process_gps_input()` did, including the fix-type mapping (0–6; others are logged and reported as `NoGps`).
- **v3 API.** Subscriptions return a `GpsInputHandle` that must be kept for `unsubscribe_gps_input()`, like every v3 subscription. v1.4.11 had one callback per plugin, replaced on each `subscribe_gps_input()` call.
- **One callback per message, per GPS instance.** Each callback gets the message just decoded (`id` = `gps_id`), not the latest stored value, so two GPS instances can't swap values between decoding and the callback.
- **Unknown values.** `heading_uncertainty_rad` and `course_uncertainty_rad` are NaN when unknown (v1.13 sent 0), `timestamp_utc_us` is 0 until the receiver has UTC, and `yaw_deg` is 0 without a heading.
- **Not generated.** `GpsInput` and its three functions are hand-maintained additions to the generated plugin files (`telemetry.h`, `telemetry.cpp`, `mocks/telemetry_mock.h`), marked `SEES`, as on `v1.4.11_dev`. They aren't in `proto/`, so re-running `tools/generate_from_protos.sh` removes them, and they aren't available through `mavsdk_server`. Re-apply them after regenerating.
- If the build doesn't define `SEES_GPS_RAW` (a dialect other than `sees`), the handler isn't registered and `subscribe_gps_input()` never fires.

Checked against PX4 v1.17 SITL (SIH), Onboard link on UDP 14540: `subscribe_gps_input()` received 39 messages in 5 s, at SIH's GPS rate. All fields decoded (`heading_uncertainty_rad` NaN and `timestamp_utc_us` 0, as SIH sends). Unsubscribing stopped the callbacks, and `gps_input()` returned the latest message.

Also check whether anything still uses the unmerged branch `ws_rtcm_length_update` (2023, Rtk plugin changes). SeesInterface2 doesn't use that plugin.

<a id="rtcm-monitoring"></a>**RTCM monitoring.** PX4 sends the RTK corrections it receives from QGroundControl on to the companion as `GPS_RTCM_DATA` (Firmware migration item #37, ported in #104). `c95c11ba3` adds `Telemetry::GpsRtcmData` to decode it. SeesInterface2's `FlightControllerPX4.cpp` publishes it to the `GPSRTCMData` buffer and the `GPSRTCMDataFlag`/`GPSRTCMDataLength` state channels, with a 5 s timeout (`RTCMMessageUpdateTimeoutS`). It must keep working. `GPS_RTCM_DATA` is in `common.xml`, which `sees` includes.
